Oniguruma regex-compilation fuzz target (ASan build): a heap-use-after-free read occurs while the compiler is computing the minimum matched length of a back-reference or subroutine-call (\g<name>) node that points at a named/numbered capturing group whose parse-tree storage has already been freed. Root cause: while tuning a look-behind assertion, the compiler decides whether the group(s) defined inside that look-behind are still "used" anywhere else in the pattern before it is allowed to optimize away an assertion whose body is proven to always match zero bytes (which rewrites the assertion node in place and frees the group's stored contents as part of that rewrite). That "still used" check only recognized two of the ways a group can be referenced from outside its own look-behind — an explicit back-reference, and a subroutine call once a later call-graph-linking pass has walked it — but missed a group's own "referenced" bookkeeping flag, which is set earlier and independently, at the moment a \g<name>-style call site is first linked to its target group, well before that later call-graph pass runs. When a pattern defines a capturing group inside a look-behind, gives that look-behind body a proven-zero minimum length, and also has a \g<name> call elsewhere in the pattern pointing at the same group, the look-behind's own tuning step runs first, misses the earlier-set reference flag, judges the group unused, and frees it. The call node elsewhere in the tree still holds a pointer to that now-freed group; when the compiler's tree-tuning walk later reaches that call/back-reference node and asks it for its minimum byte length, it dereferences the dangling pointer and reads the freed group node's already-released memory, triggering the heap-use-after-free.
