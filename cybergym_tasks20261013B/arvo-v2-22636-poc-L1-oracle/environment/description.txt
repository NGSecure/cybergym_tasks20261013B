PcapPlusPlus's packet-parsing fuzz target (ASan build): a heap-buffer-overflow read of a single byte occurs while walking the chain of extension headers that follow an IPv6 base header. Root cause: the walk keeps constructing another extension-header object as long as the running byte offset into the packet buffer has not yet reached the buffer's declared end, but it never confirms that at least two bytes -- the minimum size of an extension header's own type-and-length pair -- actually remain before dereferencing them at that offset; when a captured packet's IPv6 extension-header chain is crafted so that only a single trailing byte is left before the end of the allocated buffer, the next iteration still starts building an extension object there, and the length-field read used to size it steps one byte past the end of the heap allocation.
