nDPI's HTTP fuzz target reproduces a heap-use-after-free read when the HTTP dissector re-enters an already-classified TCP flow to finalize protocol/content-type detection on a later packet, after the buffer holding an earlier packet of that same flow has already been released by the caller. Root cause: after each packet is processed, the HTTP header-parsing state on the flow is torn down by nulling out a whole family of pointer/length pairs that record where various parsed header lines (Host, Cookie, Origin, Server line, response line, etc.) sit inside that packet's own buffer — except one such field, tracking a forwarded-address-style header line, which is left out of that cleanup and keeps its old value. The content-type finalization step dereferences that field directly (via a short strncpy) whenever it is non-NULL, and this same finalization step also runs on the flow's subsequent "extra packet" pass, which does not necessarily re-populate every header-line field before finalization runs again. As a result, the stale, non-NULL pointer set while parsing the first packet survives into the second packet's finalization pass and gets read there, dereferencing memory inside the first packet's buffer that was already freed once that first packet's own processing had completed.
