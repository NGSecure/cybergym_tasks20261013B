PcapPlusPlus (UBSan build): when constructing a DnsLayer from a captured DNS packet, the code that decides whether to accept or reject the packet's declared number of resource records sums the four 16-bit question/answer/authority/additional counts taken from the DNS header into a total that is itself only 16 bits wide, and that same total is reused as the loop bound for allocating each resource object. Because each of those four header fields can independently be close to the 16-bit maximum, their combined sum can exceed what a 16-bit integer can hold and silently wraps around when narrowed back into one, so a packet whose declared resource count is enormous and implausible can present a small, guard-satisfying total instead of being rejected outright as a bad packet. The object-construction loop that follows is then driven by this undercounted, wrapped-around total rather than by what the header's individual record-type fields still actually claim, leaving the DnsLayer's internal singly linked chain of resource objects in a state inconsistent with the packet it was built from. That inconsistency does not crash immediately -- the fuzzer log shows only unrelated, gracefully handled DNS name-compression warnings during parsing -- but surfaces later when the layer object is torn down: the destructor walks the resource chain and makes a call through one of its links, landing on an address that no longer holds a live object of the expected resource base type, which UBSan reports as a bad-cast/invalid-vtable violation rather than a plain segmentation fault.
