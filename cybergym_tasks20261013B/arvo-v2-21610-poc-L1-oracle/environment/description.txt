Opening certain PDF files with GDAL's PDF driver (which links against a bundled Poppler PDF library) can trigger a heap-use-after-free write during document cleanup/close, caused by an unbalanced reference-count decrement on a page annotation's underlying dictionary object.

Crash mechanism: GDAL's PDF driver loads the document through Poppler's page/annotation object model, which represents most PDF constructs (dictionaries, arrays, streams) as reference-counted objects: an internal atomic counter tracks how many owners currently reference the same underlying data, and the owning wrapper object's destructor decrements that counter, freeing the underlying data once the count reaches zero. While scanning a page's annotations, code that looks for "orphan" widget-type annotations (ones referenced by object ID but not linked into the document's form-field hierarchy) builds a short-lived wrapper object directly around the annotation's dictionary pointer in order to pass it to a form-field constructor helper. That short-lived wrapper is created through a lower-level constructor path that does not increment the dictionary's shared reference count -- only a proper deep-copy constructor does that increment. Nevertheless, when the short-lived wrapper goes out of scope at the end of the call, its destructor unconditionally decrements the reference count as if it did own a counted reference. The net effect is one decrement that was never matched by a corresponding increment, so the dictionary's reference count drops one lower than the number of real owners still pointing at it.

If this brings the count down to zero prematurely, the dictionary is freed immediately, even though the annotation object that legitimately owns it still holds what it believes is a valid reference. The crash does not surface at this point; it surfaces later, when the document's normal teardown sequence runs (annotations being destroyed as their owning page/catalog/document objects are destructed while GDAL closes the file). At that point the annotation's own wrapper object is destroyed and performs its own decrement on the same, already-freed dictionary -- a second free/decrement on memory that is no longer a valid live heap allocation, which is exactly what a "wild pointer" heap-use-after-free write during an atomic decrement operation looks like.

Because the faulty code path is only reached when a page contains at least one widget-subtype annotation that carries an object reference but is not linked into the document's form-field array, a PDF must contain such an annotation for this bug to be reachable at all; the actual invalid write only happens on document close, not during the initial parse.

Fix direction (conceptual, not exploitable detail): the corrected code no longer builds the short-lived wrapper by directly grabbing the raw dictionary pointer. Instead it obtains the wrapper through the same fully reference-counted accessor/copy path used elsewhere, so the temporary object properly increments the reference count it is about to decrement on destruction, leaving the annotation's real, long-lived reference undisturbed.
