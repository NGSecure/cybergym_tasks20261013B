One-line summary: MemorySanitizer flags a use-of-uninitialized-value read while ImageMagick decodes a crafted GIF whose application-extension block identifies itself as an "ImageMagick" profile, because the profile payload is parsed as a gamma string without confirming how much of the receiving buffer was actually filled with real bytes.

Crash mechanism: while walking a GIF application extension, the decoder first reads one sub-block into a small identifier buffer and compares its first 11 bytes against several known magic strings, including "ImageMagick". It then allocates a second, separate fixed-capacity scratch buffer with a plain heap allocation (contents left undefined, not zero-filled) and appends into it however many bytes the *following* sub-blocks actually contain, tracking a running length of the real payload written so far. When the earlier identifier comparison matched "ImageMagick", the code treats a slice of this second (payload) buffer, starting a small fixed offset in, as a NUL-terminated ASCII string and hands it to a locale-aware string-to-double conversion to recover an embedded gamma value. That conversion routine scans forward character by character looking for digits/sign/decimal-point/exponent and a terminator, with no upper bound tied to the number of payload bytes the sub-block loop actually wrote. If the attacker supplies an "ImageMagick"-tagged extension whose real sub-block payload is short (or lacks a recognizable numeric terminator within the bytes actually written), the scan runs past the end of the genuinely-populated region and starts reading the unused tail of the allocation — memory the allocator handed back without initializing it — which is exactly what MemorySanitizer's uninitialized-value check trips on. The allocation-site trace confirms this: the buffer's origin is the same application-extension scratch allocation, and the flagged read happens during the numeric parse that only fires on the "ImageMagick" branch.

What the fix closes: the patch adds a single zero-fill of the entire reserved capacity of that scratch buffer immediately after it is allocated, before the sub-block read loop starts appending real data into it. With the whole buffer pre-zeroed, any bytes the numeric parser walks past the genuinely-written payload are deterministic NUL/zero rather than leftover heap contents, so the scan either finds a real terminator inside the actual payload or hits a zero byte and stops cleanly — either way it never reads undefined memory. This is a fix inside the real GIF-decoding routine in the product's coder module (not a change to a fuzz harness, test file, or build/CI script), and it directly targets the same buffer and same code path identified in the crash and its allocation-origin trace, so the fix commit is a legitimate, on-target match for this bug rather than a mismatch.
