A software TPM2.0 reference-implementation command-execution fuzz target (UBSan build): an out-of-bounds array-index computation occurs while trimming trailing zero bytes from an authorization value that was just parsed out of an incoming command's password-authorization session area, reached during the session-processing step that checks a password-authorization session before the rest of command dispatch runs. Root cause: the trimming helper first computes the address of what it assumes is the last used byte of a fixed-size on-stack authorization buffer, by subtracting one from the buffer's recorded length, and only afterward enters a loop that walks backward while that length is greater than zero. When the parsed authorization value has a recorded length of zero (an authorization field in the incoming command that decodes to an empty value), that length-minus-one computation is done as a signed operation and produces a negative offset, so the very first thing the helper does is form a pointer one element before the start of the fixed-size buffer -- before the length-is-positive guard is even checked, and before any byte is actually read through that pointer. Forming this out-of-bounds address is itself undefined behavior even though the subsequent loop body never dereferences it in the size-zero case. The fix restructures the helper so the length-is-positive condition is evaluated first (short-circuiting) and the indexed byte access only ever happens after that check passes, so a zero-length authorization value no longer causes any out-of-bounds address to be formed.
