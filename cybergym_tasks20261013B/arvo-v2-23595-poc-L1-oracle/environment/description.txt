Skia's SVG parser (same named-color lookup reached through SkSVGDOM's attribute-parsing path, this time exercised by the svg_dom fuzz target running under honggfuzz + ASan) resolves a CSS-style named color for an SVG paint attribute by first tokenizing the requested color-name string into fixed-width six-character chunks, before any table lookup happens at all: it repeatedly consumes up to six letters at a time from the name, packs each chunk into a 32-bit word, and stores that word into a small array sized to hold exactly four such chunks (room for up to 24 letters total) using a cursor pointer that advances by one slot after every store.

Root cause: the loop that performs this tokenization keeps consuming six-letter chunks until it hits a non-letter character or runs out of remaining input length — it never checks how many chunks it has already produced against the fixed capacity of the array those chunks are being written into. A color-name-like attribute value made of more than 24 consecutive letters therefore drives the tokenizer to produce a 5th chunk (and keeps going for as many more as the input supplies), and the store for that 5th chunk writes through the cursor pointer one slot past the end of the fixed-size, stack-allocated array — a stack-buffer-overflow write, landing just past the array in the same stack frame. This happens entirely within the tokenization step, before the binary-search table-lookup logic that consumes these chunks ever runs.

fix_commit assessment: the recorded fix commit (15ee455939ff8c44be22158fb6e36ae02cc5ba9e) does not add a bounds check to the old tokenization loop — it replaces the entire named-color lookup implementation. The bit-packed lookup table and the hand-rolled tokenize-then-binary-search algorithm (including the fixed-size chunk array this id's bug overflows) are deleted outright and replaced with a plain array of {name, red, green, blue} records searched by direct string comparison; there is no longer any fixed-size intermediate chunk buffer for a color name to overflow. This is a full replacement of the vulnerable code path, not a narrow one-line bounds fix, and it is confirmed to eliminate exactly the defect this id's proof-of-concept exercises: comparing this id's own vulnerable and fixed sources directly shows the fixed-size chunk array and its unbounded fill loop are gone entirely in the fixed build.

This id shares its crash_function/dedup_token with a sibling id (23395) that also crashes inside the same named-color lookup function, but the two are independent, distinct defects rather than a duplicate filing of one bug: this id's failure is a WRITE that overruns the small on-stack tokenization buffer before any table lookup happens, while the sibling's is a READ that overruns the lookup *table* later, during the binary search's bound-walking step — different memory objects, different access types, triggered by structurally different inputs (this id's proof-of-concept is a long, ~1.5KB input built to produce many chunks; the sibling's is a short, 22-byte input), reported about a week apart by two different fuzzing engines against the same source revision range. Notably, this id's own fix (a full rewrite) happens to also eliminate the sibling's table-walking defect as a side effect of removing the whole old algorithm — but the sibling's own, separately-committed fix predates this rewrite and only patches the table-walking bound defect, leaving this id's tokenization-buffer overflow completely intact (verified directly in the sibling's fixed source: the fixed-size chunk array and the loop that fills it are byte-for-byte unchanged there). That one-directional, narrowly-scoped sibling fix is decisive: if the two crashes were really the same bug, the sibling's fix would have closed both, but it only closes its own. The two are confirmed independent.
