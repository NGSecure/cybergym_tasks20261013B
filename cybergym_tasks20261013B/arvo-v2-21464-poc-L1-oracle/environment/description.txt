open62541's JSON decode/encode fuzz target (libFuzzer + ASan) drives the OPC UA JSON decoder's top-level entry point on attacker-controlled JSON input. A heap-use-after-free read occurs during the error-cleanup pass that the entry point runs after an inner decode step reports failure partway through the input.

Root cause: while decoding an unwrapped ExtensionObject body that lives inside a Variant, the decoder first allocates a buffer to hold the array element it is about to build, then proceeds to decode that element's remaining fields one by one. If that field-by-field decode fails before finishing, the function frees the just-allocated buffer on that error path but leaves the Variant's own data pointer still pointing at the now-freed block instead of resetting it to a null pointer. Because the overall decode call still returns failure, the top-level cleanup routine treats the partially-built result as if it were valid output and walks it to release everything that was allocated during the failed decode: it descends through the Variant's array-teardown path and recurses into the freed element's own member-clearing logic, which ends up reading one of the element's struct fields (a node-identifier value) directly out of memory that had already been freed a few calls earlier in the same decode attempt. The missing null-out after the early free is what turns an already-failed decode into a use of freed memory during its own error-handling path, rather than a clean, side-effect-free failure return.
