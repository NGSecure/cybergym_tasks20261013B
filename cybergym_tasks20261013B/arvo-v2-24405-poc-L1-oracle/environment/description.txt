PHP's Zend compiler crashes purely from *compiling* (no execution needed) a script that calls assert() with a single, non-string-literal argument expression that contains a nullsafe property or method access (`$x?->y` / `$x?->y()`), because whenever assertions are enabled the compiler unconditionally builds a source-text rendering of that argument expression (to use as the assertion's default failure message) by recursively walking its parsed AST and re-serializing each node back into PHP syntax into a small heap-backed growable string buffer owned by the top-level export call. That recursive AST-to-source serializer is one large switch keyed on the AST node's kind, with dedicated, explicitly-written cases for ordinary (non-nullsafe) property access and method-call nodes; nodes are two- and three-child structures respectively, matching what those cases expect. Nullsafe `?->` access was added to the language as its own pair of node kinds, structurally identical to (same child layout as) the ordinary property/method-call nodes, but the serializer's switch was never extended with matching cases for them. The switch's catch-all for "no case matched" is not a normal default handler — it's annotated to tell the compiler this branch is provably unreachable, on the assumption that every node kind the parser can produce is already listed above it. That assumption became false the moment the nullsafe node kinds started flowing through this function without a case, so reaching the branch at runtime is undefined behavior rather than a clean error path: instead of failing safely, execution effectively falls through into the buffer-growing/copy logic used by the ordinary cases, which then runs with output-length/position bookkeeping that was never actually set up for this node, producing an out-of-bounds-looking access right at the edge of the caller's small string-buffer local variable. Root cause: an incomplete-case-coverage bug in a switch whose default branch was compiled under a "this can never happen" assumption that a newly added expression-node kind silently invalidated, so any use of that new syntax inside a to-be-serialized assert() argument drives the switch into its unreachable branch and corrupts adjacent state instead of tripping an assertion or falling back to sensible output. The fix adds the two missing cases (rendering them with the nullsafe arrow instead of the plain one), which is a source-level, compile-time-only change with no runtime/data dependency — closing the gap means every node kind the parser can actually produce is once again listed, so the "unreachable" branch is unreachable again.
