The fmt C++ formatting library suffers a heap-buffer-overflow READ triggered while resolving a named argument (an "arg name = value" pair) during a formatting call.

Root cause: when the formatter needs to match a requested argument name against the names of the named arguments that were passed in, it does not keep and reuse the exact length that was already known when each named argument was constructed. Instead, at lookup time it rebuilds a string view for the stored argument name from a bare character pointer, using a constructor that determines the name's length by scanning forward for a NUL terminator (i.e. an implicit strlen-style scan). This silently assumes every argument-name buffer is a conventional null-terminated C string, even though the original API accepted an explicit (pointer, length) view that need not be null-terminated at all.

If the caller supplies an argument name backed by a heap buffer sized to hold exactly the name's characters and nothing more (no trailing NUL byte immediately after the last real character), the length-rediscovery scan keeps reading past the end of that allocation. The read lands in the heap region immediately following the buffer (ASan's redzone), and the sanitizer reports it as a heap-buffer-overflow read. The overflow happens purely from mismatched assumptions about string termination during named-argument name lookup/formatting — no other part of the format string or the argument's value is involved.

The upstream fix does not preserve the length end-to-end; instead it tightens the contract in the other direction. The stored named-argument name is changed from a (pointer, length) view to a bare pointer, and the public API for constructing a named argument is narrowed to only accept a conventional null-terminated C string (rejecting arbitrary non-terminated string views outright). The fuzz harness itself is also updated to always allocate its argument-name buffer with room for, and an explicit, trailing NUL byte. In other words, the fix does not stop scanning for a terminator at lookup time — it guarantees a terminator is always present at the right offset, closing the gap between what the API assumed and what callers were actually allowed to supply.
