libzmq's WebSocket engine fuzz target (test_bind_ws_fuzzer, UBSan build): a bad-cast/use-after-free fires when the engine's inbound-data event handler reaches its normal end-of-processing step and calls flush() through its stored `_session` pointer, but that pointer is stale — the zmq::session_base_t object it used to reference is gone, and the sanitizer reports the target memory as an invalid (all-zero) vtable rather than a live session_base_t. Root cause: inside the engine's outbound message-send routine, whenever the WS-specific message-producer callback returned failure, the pre-fix code treated every such failure identically — it simply stopped the send loop and let the rest of the function keep running as normal. For the WebSocket engine specifically, that same failure can instead be an internal signal (surfaced through `errno == ECONNRESET`) that the connection has already been torn down at the protocol level; handling that teardown synchronously destroys the engine object itself — the very object whose method is still executing — via its normal error-and-unplug-and-delete-self path (which does null out its own session pointer as part of that path, before the object is freed). Because the pre-fix code never special-cased this failure, it let control fall through and keep touching that engine after this self-destruction had already happened: either later code in the same call path dereferenced fields of the now-freed engine, or — consistent with the actual crash trace, which shows the fault surfacing through a separate inbound-event dispatch from the poller's event loop rather than inline in the same call — a second, already-queued readiness event for the same socket, delivered later in the same poller batch, was dispatched to the freed engine object, whose stored session pointer was then read out of already-freed memory and used in the flush() call that crashes.

The fix special-cases exactly this condition inside the outbound message-send routine: when the message-producer callback fails with `errno == ECONNRESET`, the function now returns immediately instead of falling through to the old "stop the loop and keep going" behavior, so nothing further reads or dereferences the engine object once it has torn itself down along this path; any other producer-callback failure (a genuine end-of-messages condition, where the engine legitimately stays alive) still falls through to the original behavior unchanged.
