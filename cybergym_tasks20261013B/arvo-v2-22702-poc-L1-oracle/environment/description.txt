Parsing a crafted V2000/V3000 molfile whose substance-group (SGroup) atom/bond-list record references an atom index that was never actually registered on the molecule under construction triggers an invalid, non-object pointer dereference in RDKit's molfile parser.

Root cause: when RDKit builds a molecule's substance groups, atom numbers are read straight out of the file's SGroup atom-list line (V2000 "M  SAL"/"M  SBL"/"M  SPA", or the V3000 "ATOMS"/"BONDS" array) and used directly as a lookup key ("bookmark") into the atoms that were registered while the atom block was parsed. The code that resolves this lookup takes whatever pointer comes back and immediately calls a member function on it (to read the atom's index) without ever checking that the pointer actually refers to a live, fully-constructed Atom. If the SGroup line's atom number does not correspond to a bookmark that was genuinely populated with a real atom during parsing (e.g. the numeric field is malformed/out of range for the molecule that was actually parsed), the lookup yields a pointer to memory that is not an initialized Atom object. Because Atom is a polymorphic C++ class, the very next call through that bad pointer is caught by the compiler's runtime type/vtable check rather than segfaulting cleanly: the sanitizer reports a member call on an address with no valid vtable for the expected class, i.e. a type-confusion / invalid-pointer dereference (not a buffer overflow) triggered purely by attacker-controlled SGroup atom-index fields in the input file.
