An invalid C++ downcast (undefined-behavior "bad-cast") fires while RDKit is finishing up parsing of a SMILES string that contains an extended-SMILES (CXSMILES) block, specifically while post-processing per-atom CXSMILES pseudo-atom labels right after the core SMILES grammar has been parsed into a molecule.

Several of these pseudo-atom labels (Marvin conventions such as "any heteroatom", "any heteroatom including H", "any atom", "any atom including H", etc.) are each handled by attaching a small, purpose-built query object to the atom, and each label has its own tiny factory helper that builds the right kind of query object and returns it. Most of these sibling helpers legitimately build and return an "equality" query object — one that carries an actual comparison value and can be asked "does this atom equal X?". The helper responsible for the "any atom, including H" label is different: rather than allocating its own equality-style object, it takes a shortcut and reuses a second, unrelated factory whose job is to build a bare, always-succeeds placeholder query (used elsewhere for reset/blank markers) that has no comparison-value slot at all and is a plain base type, not the equality-query subtype. To keep its own function signature consistent with its equality-returning siblings, this helper then blindly reinterprets ("downcasts") the pointer it got back as if it pointed to the equality-query subtype, and hands that pointer back to its caller.

The object that was actually heap-allocated by the reused factory is genuinely only an instance of the plain base query type: its vtable/runtime type identifies it as the base class, and it lacks the extra state the equality subtype expects. A downcast from a base-class pointer to a derived-class pointer is only well-defined in C++ when the pointed-to object really is an instance of that derived class (or something further derived from it). That is never true here — the object is exactly the base type and nothing more — so the cast itself is undefined behavior the moment it executes, independent of whether the equality-specific members are ever subsequently read or written. This is exactly what the sanitizer's vptr check reports: the address being downcast points to an object whose runtime type is the plain base query class, not the equality-query class the code casts it to.

Reaching this is purely a parsing-time effect with no further preconditions: any input SMILES string whose CXSMILES suffix assigns the Marvin "any atom, including H" pseudo-atom label to one of the molecule's atoms drives the label post-processing loop to call this specific helper for that atom, and the invalid downcast happens unconditionally as the very first thing the helper does, before the resulting pointer is even attached to the atom or otherwise used.

Note on fix relevance: crash.json's fix_commit has been corrected to a9010da8a4af17479c706f2cf4e8c6acdc1585ce (matching the upstream-recorded "fix" reference for this id) after checking the full candidate commit list — the previously recorded fix_commit was an unrelated, much larger feature commit (adding a new tautomer-aware substructure-query module) that never touches the function or file responsible for this crash at all. The corrected commit directly patches the root cause described above: the helper's own return type is changed to match the plain base type the reused factory actually produces, and the invalid downcast is removed outright rather than worked around, so the object handed back is honestly typed as what it is. This fix is exercised by the same reproducer (parsing a SMILES string with a CXSMILES "any atom, including H" pseudo-atom label): after the fix the helper no longer performs any type-punning downcast on that code path.
