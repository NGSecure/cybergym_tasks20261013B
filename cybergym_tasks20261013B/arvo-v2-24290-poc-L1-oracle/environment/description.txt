libvips's smartcrop fuzz target crashes with a SEGV (wild-address read) inside the pipeline's XYZ-to-Lab colour-space conversion step while a worker thread is regenerating an image region, after honggfuzz feeds it a deliberately corrupted TIFF (the run log is full of out-of-spec IFD tags, bad field counts, wrong strip/tile metadata, and similar TIFF-loader complaints right up to the crash). Root cause: for each of the three colour channels, the conversion step normalizes the incoming pixel value against that channel's reference white-point constant and turns it into an integer table index plus a fractional remainder, used to look up and linearly interpolate between two adjacent entries of a fixed-size precomputed cube-root lookup table. The index is produced by clamping the scaled value into the table's valid range with a small generic clamp helper built purely from relational (less-than/greater-than) comparisons. Earlier in the long chain of region-generate callbacks that decode, embed, convolve, and recombine the corrupted image data before it reaches this conversion, the per-pixel value being clamped degenerates into a non-finite (NaN) floating-point value. Because every relational comparison against NaN evaluates to false by definition, the comparison-based clamp takes neither its "too low" nor its "too high" branch and simply returns the NaN value unchanged instead of forcing it into range. That NaN is then implicitly converted to an integer table index, producing an effectively arbitrary/undefined index value, and the subsequent table lookup dereferences memory far outside the table object -- the wild-address read that aborts the worker thread. This was a short-lived regression on libvips' master branch (roughly one day, per the upstream report): one pull request introduced the comparison-based clamp on this scaled channel value, and the very next day another pull request reverted it back to a floating-point-aware clamp built on the standard NaN-safe max/min primitives, which by definition return the non-NaN operand whenever exactly one input is NaN and so force a NaN channel value into the valid table range instead of letting it pass through untouched. The recorded fix_commit is that reverting commit, and it touches only the three clamp call-sites (one per colour channel) inside the crashing function -- it swaps in exactly the NaN-safe clamp needed to close this exact defect, so it is a precise, trustworthy fix for this crash rather than an unrelated or approximate one.
