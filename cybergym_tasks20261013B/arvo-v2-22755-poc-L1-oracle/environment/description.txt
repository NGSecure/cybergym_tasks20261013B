nDPI's packet-processing fuzz target (ASan build): when a captured packet's datalink type is IEEE 802.11 with a leading radiotap header, the code computes the offset of the trailing LLC/SNAP header using the radiotap header's own attacker-controlled length field, plus a fixed extra offset that gets added whenever the frame-control bits mark the frame as an 802.11 data frame, but never checks that this computed offset plus the LLC/SNAP header size still fits inside the packet's actual captured length. A short, malformed 802.11/radiotap capture pushes that offset past the end of the fuzzer-supplied input buffer, so reading the first byte of the LLC header at that offset performs a 1-byte heap-buffer-overflow read just past the allocated buffer.
