muparser's expression evaluator (fuzz target: set_eval_fuzzer, ASan build): evaluating a specific expression triggers a heap-buffer-overflow READ of 8 bytes while executing already-compiled bytecode. The tokenizer's syntax-flag state machine tracks, after each token, which token kinds are legal next; the state entered right after accepting a unary/infix arithmetic operator (e.g. a prefix '+') wrongly permits an argument-separator (comma) to follow directly, even though an infix operator by definition still requires an operand before anything else can legally come next. An expression built from long chains of such infix operators glued together across comma-separated sub-expressions therefore tokenizes and compiles without error instead of being rejected at parse time. When the compiler's static pass walks the resulting token/opcode stream to determine how deep the runtime evaluation stack can get, it under-counts the depth this particular repeated-infix-then-separator shape actually drives the stack to. The evaluation-stack buffer used when the compiled bytecode is later executed is a heap allocation sized directly from that under-counted maximum, so once evaluation runs far enough to read back the accumulated final result, it reads one stack slot past the end of that undersized heap buffer.
