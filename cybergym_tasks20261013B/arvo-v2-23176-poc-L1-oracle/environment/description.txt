LibRaw's Pentax raw decoder builds its Huffman lookup table entirely from values taken out of the input file and can leave part of that table unset. The routine that sets up decoding declares a stack array of a few thousand entries and, for each of a handful of code lengths, reads a pair of file-controlled values (a starting index and a length code) and fills only the table slots that fall inside the range computed from that pair; one slot is then set separately, but nothing guarantees the file-supplied index/length pairs jointly cover every remaining table entry. With a crafted, corrupted set of these values (as in this test case, flagged with "unknown file: data corrupted" while the file's structure was being parsed) the fill step leaves some table indices untouched, so they still hold whatever garbage was on the stack when the routine was entered. Decoding then proceeds row by row through a table-walk step that reads a Huffman-coded difference; when the bit pattern taken from the compressed stream happens to index one of the never-initialized slots, the walk consumes uninitialized content, which MemorySanitizer reports as a use-of-uninitialized-value, with the origin traced back to the table's allocation in the setup routine. The recorded fix_commit ("FP DNG: check for bit range: 16, 24, 32 only") does not address this: it only tightens bit-depth/sample-format validation used when the file-format-detection code chooses among floating-point and deflate DNG decoders, and it never touches the Pentax decoding path at all. A genuine fix for this bug would instead need to either fully initialize the table before the fill step or validate that the file-supplied index/length pairs cover the whole table before decoding starts -- neither of which this commit does.
