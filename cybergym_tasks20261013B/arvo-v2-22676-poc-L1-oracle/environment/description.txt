nDPI's packet-analysis example harness (MemorySanitizer fuzz target) crashes with a SEGV caused by a READ when a helper that duplicates a C string into freshly allocated memory computes the source string's length: the pointer it is handed is not a real address. The call site sits in the packet reader's per-flow export step, in the branch that copies out a completed flow's negotiated TLS/SSL fields once the flow has been classified (or guessed) as an SSL/TLS session; among those fields is a heap-allocated copy of the negotiated ALPN protocol list, which the exporter only reads if the field looks non-empty. Root cause: that ALPN slot lives inside a per-flow record that is shared/reused across several unrelated protocol classifiers as the engine narrows down what a flow actually is, and it is meant to be written exactly once, by the TLS ClientHello parser, via a real heap allocation. The flow that trips this crash never goes through that TLS ALPN parser at all - it is a flow the STUN classifier keeps re-examining packet after packet, because the logic meant to give up on a flow as "not STUN" and stop touching its shared per-flow state only fires once an accumulated packet count crosses a threshold (previously a fairly generous one), rather than after the classifier's very first pass; the same classifier was also still reachable for connections that were never valid candidates for it in the first place. By the time this flow later gets folded into the SSL/TLS bucket during the engine's final protocol-reconciliation step and handed to the exporter, the bytes sitting in the ALPN pointer slot are stale leftovers from that extended, never-cleaned-up classification churn rather than a real allocation or a null pointer, so the length computation dereferences a wild address.
