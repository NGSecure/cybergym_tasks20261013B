ImageMagick's own JPEG2000 (JP2) decoding path, after the vendored openjpeg library has already finished decoding an image's tile-component sample data into per-component heap buffers, copies those decoded samples into ImageMagick's internal pixel representation by looping over the output image's rows/columns and computing, for each component, a linear index into that component's own sample buffer from the component's horizontal/vertical subsampling factors. Root cause: the index formula is built from the overall output image's column/row counts rather than being validated against that particular component's own actual decoded width and height, so when a component's real dimensions don't match what the subsampling-based formula assumes (an irregular/inconsistent channel geometry across the image's components), the computed index runs past the end of the small heap buffer openjpeg allocated for that component's samples, producing an out-of-bounds heap read while copying pixel data. The defect is in ImageMagick's own post-decode pixel-copy loop, not in the vendored openjpeg decoder itself, which completes the actual JPEG2000 decode successfully before this later indexing step overruns the buffer.
