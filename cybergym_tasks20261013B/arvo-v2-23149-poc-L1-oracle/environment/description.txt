Perfetto trace_processor (ASan build): feeding the trace-parsing fuzzer a crafted proto trace whose clock-snapshot packet re-registers an already-known clock domain with different unit/incremental-mode properties, followed by a later packet whose timestamp has to be converted across clock domains through that same desynchronized domain, causes an 8-byte heap-buffer-overflow read deep in the trace processor's clock-conversion code. Root cause: when the snapshot-recording step's per-domain consistency check rejects a domain because its properties changed since first registration, that domain's entry is only partially recorded, so its parallel per-domain snapshot-id/timestamp vectors end up one element shorter than the other domains that did get every domain's entry appended -- the domains silently fall out of sync with each other. A later timestamp conversion that has to hop through that now-shorter domain binary-searches its sorted snapshot-id vector for the shared snapshot id; because that id was never recorded there, the search legitimately comes back empty, but the surrounding code only verified this via a debug-only assertion that is compiled out in this (non-debug, fuzzer/ASan) build. With the guard compiled away, execution falls through anyway, computes an index equal to the (undersized) vector's length -- i.e. one past its last valid element -- and uses that out-of-bounds index to read the corresponding entry out of the parallel timestamp vector, landing exactly one 8-byte element past the small heap allocation backing it.
