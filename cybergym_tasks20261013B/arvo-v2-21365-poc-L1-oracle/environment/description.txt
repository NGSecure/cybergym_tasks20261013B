One-sentence summary: In nDPI's NetBIOS protocol dissector, a NetBIOS "first-level encoded" name field is decoded from a computed offset into the UDP/TCP payload without first checking that the offset actually falls inside the captured payload, and the decoding helper itself trusts a length value taken from the very first byte it reads instead of the real remaining input size, producing a 1-byte heap-buffer-overflow read.

Crash mechanism:
- The NetBIOS dissector's top-level search routine recognizes candidate NetBIOS traffic on UDP port 137, UDP port 138, and TCP port 139 using a series of header-field and minimum-length checks, then hands the flow off to a small connection-setup helper.
- That connection-setup helper picks a byte offset ("off", either of two small fixed values) into the payload based on the value of a single payload byte, and passes a pointer at that offset straight into the NetBIOS name-decoding routine — with no check that this offset is actually still within the payload's captured length before making the call.
- The name-decoding routine (the function where the crash is reported) is only given a pointer and an output-buffer size; it has no parameter describing how much input data is actually available at that pointer. Its very first action derives a decode-loop iteration count purely from the byte it reads at the pointer, and only afterwards validates that count against the *output* buffer size — never against how much input remains.
- The upstream length checks in the top-level search routine only guarantee that the payload is long enough to safely read the handful of header bytes used for protocol classification; they say nothing about whether the payload actually extends far enough to cover the name field at the chosen offset. When a recognized-as-NetBIOS packet's payload ends at or before that offset, the pointer handed to the decoding routine already points at or past the end of the payload's heap allocation, and the very first read inside that routine (the byte used to compute the decode length) reads past the buffer — the reported heap-buffer-overflow READ of size 1.
- Call chain matches the report exactly: the name-decoding routine, called from the connection-setup helper, called from the UDP flow-check dispatcher, called from the top-level packet-processing entry point — i.e. this is reached via the UDP dissection path.

Fix verification: fix_commit 4f370fe7c49cb38125cff2a1411261011e433c94 (confirmed on GitHub against the exact commit hash, not just the file name) modifies precisely this code: it adds an explicit input-length parameter to the name-decoding routine and checks the decode length against that real remaining-input size before the decode loop runs, and it adds an offset-vs-payload-length guard in the connection-setup helper before the decoding routine is invoked at all. Both changes sit directly on the crashing function and its immediate caller, matching crash_function/crash_file/crash_line in crash.json, and this matches the recorded differential result (fix build does not crash, vul build does). fix_commit and fix_files in crash.json are confirmed correct as-is; no correction was needed.
