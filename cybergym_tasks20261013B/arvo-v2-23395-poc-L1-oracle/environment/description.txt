Skia's SVG parser (reached through SkSVGDOM's attribute-parsing path, exercised by the svg_dom AFL fuzz target under ASan) resolves a CSS-style named color for a `fill`/`stroke`-like SVG paint attribute by tokenizing the requested color name into fixed-width six-character chunks and binary-searching those chunks against a compact, bit-packed lookup table holding every recognized CSS color name (each record is one or more 32-bit words; the first word of a record is tagged by having its sign bit set).

Root cause: whenever the binary search's probed record compares as lexically "less than" the name being looked up, the code advances the search's low bound past that record by walking forward one packed word at a time until it finds the next record's tagged start word. That forward walk has no upper-bound check against the end of the table — it simply keeps reading words and testing the sign-bit tag until it finds one. The search's high bound is pre-adjusted (backed off by a few words) specifically to keep the *probe* itself inside the table for a "compare against the very last entries" scenario, but that adjustment does not protect this separate forward-walk-for-the-next-record-boundary path. When the queried name sorts lexically after every entry near the tail of the table (i.e., past the last recognized color name), advancing the low bound this way runs the forward walk off the end of the table before it ever finds another tagged start word, so it reads one 4-byte word immediately past the table's storage — a global-buffer-overflow read, landing exactly at the first byte past the table (matching the reported "0 bytes to the right of" the table).

fix_commit assessment: the recorded fix commit (4190f27b41ffb710e7d56fe1f1883cd8cd8b853e) rewrites exactly this bound-advancing logic — it introduces explicit helper routines that locate a record's start and are guarded by assertions confirming the index they return is still inside the table, and it adds an explicit loop-termination check ("low bound caught up to high bound → stop, not found") before any further advancing is attempted. The tokenization step that builds the six-character chunks earlier in the function, and the small fixed-size on-stack buffer that step writes those chunks into, are left completely untouched by this fix — it is narrowly scoped to the table-walking bound defect and does not touch the tokenization step at all.

This id shares its crash_function/dedup_token with a sibling id (23595) that also crashes inside the same named-color lookup function, but the crashes are independent, distinct defects, not a duplicate OSS-Fuzz filing of the same bug: this id's failure is a READ that overruns the *lookup table* during the binary-search bound-walking step, while the sibling's is a WRITE that overruns the small on-stack *chunk buffer* during the earlier tokenization step — two different memory objects, two different access types, triggered by two structurally different inputs (this id's proof-of-concept is a short, 22-byte input; the sibling's is a much longer, ~1.5KB input), reported about a week apart by two different fuzzing engines against the same source revision range. Each id's own fix commit addresses only its own defect: this id's fix leaves the sibling's tokenization-buffer defect completely intact (verified by inspecting the fixed source directly — the fixed-size chunk buffer and the loop that fills it are byte-for-byte unchanged by this commit), so a PoC built for the tokenization-buffer bug would still crash under this id's own "fixed" build, and vice versa. The two are confirmed independent.
