PcapPlusPlus's packet-parsing fuzz target (ASan build): reconstructing a TCP-carried TLS handshake into a Packet object triggers a heap-buffer-overflow read while parsing an SSL/TLS CertificateRequest handshake message. Root cause: the message constructor first checks that the raw handshake bytes are at least as long as the fixed header plus a one-byte certificate-types-count field, then separately re-derives the message's own payload length from a 3-byte length field embedded inside that same handshake header — a value fully controlled by the crafted packet and never validated against that same minimum size. When this self-declared payload length is smaller than the header-plus-count minimum, subtracting the header size from it underflows (both operands are unsigned), producing an enormous "bytes remaining" value. The bounds check meant to clamp the attacker-supplied certificate-types count (read straight from the packet bytes, up to 255) against the real number of remaining bytes is therefore never true, so the count is used unclamped. The subsequent per-type loop then walks one byte at a time well past the end of the actual captured packet buffer, reading out of bounds.
