OpenSC's PKCS#15 card-binding fuzz target (honggfuzz/ASan build): while selecting a file, the ASEPCOS card driver's FCI handler decodes a security-attribute byte string that the card returned and stores a freshly allocated copy of exactly that many bytes on the file object. A second pass then walks this stored buffer entry by entry to translate each security condition into access-control rules: it first confirms at least five bytes remain and that the first two bytes carry the expected access-mode tag, then reads the mode byte and a following one-byte condition tag; for two of the possible condition tags, before consuming the entry it checks that the buffer holds at least as many further bytes as a length byte occupying byte offset four of the current entry claims are needed. Because that length check compares against only the first four bytes of the entry rather than the full five-plus-length size, a length byte of zero always satisfies it regardless of how many bytes actually remain, so the code proceeds to read one more byte immediately after the length byte as the condition's associated value — even though a declared length of zero means no such byte was ever appended when the entry was built. When this zero-length variant is the very last entry in the stored buffer, that extra byte lies one past the end of the allocation, producing a one-byte out-of-bounds heap read. The fix rejects the zero-length case for both affected condition tags outright (treating it as an invalid security condition instead of trying to consume a nonexistent value byte), closing exactly the gap that let the length check pass without any value byte actually being present; a second, unrelated tweak in the same patch just rewords the outer loop's continuation test without changing its behavior (the count driving that loop is unsigned, so the two forms are logically identical).
