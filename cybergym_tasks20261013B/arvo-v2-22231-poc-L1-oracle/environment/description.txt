htslib's CRAM slice decoder computes an MD5 digest over an embedded reference sequence to validate it against the checksum recorded in the slice header, but the check that is supposed to reject an embedded-reference block too small for the declared reference span is off by one: it compares (span - 1) against the block's decompressed size instead of comparing the span itself, so a declared span exactly one byte larger than the actual block still passes as valid. Root cause: because the digest-hashing length is taken directly from that unvalidated span, the byte count handed to the hashing routine ends up one larger than the heap-allocated reference block backing it, so hashing the "reference" data reads one byte past the end of that block, producing a heap-buffer-overflow read.
