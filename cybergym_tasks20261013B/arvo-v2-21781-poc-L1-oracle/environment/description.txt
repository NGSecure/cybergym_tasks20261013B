nDPI's TLS/SSL protocol dissector reads uninitialized heap memory while walking the extension list of a parsed Server Hello handshake message.

When nDPI recognizes a TLS/SSL flow, it copies the reassembled handshake bytes into a heap buffer that is allocated but not zero-filled, then hands that buffer to the Server Hello parser. That parser first reads a 2-byte "extensions total length" field and then loops, reading each individual extension's 2-byte type and 2-byte length fields at an advancing byte offset into the buffer. Before each iteration it checks that the offset still falls inside the buffer, but the check is written with the wrong arithmetic: it allows the offset to advance up to a few bytes further than the buffer's actual valid length before it triggers. Because of that slack, the loop can read the type/length fields from bytes that lie just past the genuinely-populated portion of the handshake buffer -- bytes that were never written by the packet-copy step and so still hold whatever the allocator happened to leave there.

Under a memory-sanitizer build, that read of never-initialized bytes is flagged as a use-of-uninitialized-value defect. It requires no attacker-controlled overwrite of adjacent memory and does not need the value read to be attacker-chosen -- the defect is that the code trusts data it never actually received, not that the data is meaningfully forged. Triggering it only needs a TLS Server Hello whose declared extensions region is a few bytes shy of covering the full extent the (miscalculated) bounds check will tolerate, so the parser walks slightly beyond what was really captured.

The fix corrects the loop's boundary comparison so that the check requires the full 4 bytes of the next extension header to fit strictly within the buffer's actual valid length, closing the small window that let the parser read past initialized data.
