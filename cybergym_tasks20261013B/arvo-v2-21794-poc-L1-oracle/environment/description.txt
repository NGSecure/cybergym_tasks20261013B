fmt's named-argument formatting fuzz target triggers a 16-byte stack-buffer-underflow read while resolving a format argument by its numeric index inside the library's argument-storage container. Root cause: the container keeps arguments in one of two representations, chosen purely by how many arguments were passed — a small inline "packed" array used while the argument count stays within a fixed maximum (this fuzz target passes exactly one argument, so it always takes this packed path regardless of the argument being named), and a separate dynamic/unpacked representation used only once that maximum is exceeded. The bounds guard on the packed lookup path compared the requested numeric index to that maximum with a strict greater-than test instead of greater-than-or-equal, so an index exactly equal to the maximum was wrongly treated as still valid and let through instead of being rejected before the lookup. The lookup then reads one argument slot at that out-of-range index directly from the caller's on-stack formatting-handler object, landing one slot past the region actually populated with argument data, which is what AddressSanitizer reports as the underflow read.
