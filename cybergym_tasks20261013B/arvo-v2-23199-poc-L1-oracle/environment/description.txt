libmpeg2's MPEG-2 video decoder (ASan build, libFuzzer harness) crashes with a SEGV on a wild write address inside the plain memcpy() that a field-weave deinterlacing step uses to reconstruct output picture rows from the top and bottom fields, invoked from a background decode/deinterlace worker thread after the current picture has already been parsed and reconstructed. That row-copy routine performs no bounds checking of its own: it simply loops for a caller-supplied row count, copying a caller-supplied byte width per row while advancing its source and destination pointers by caller-supplied strides each iteration -- it fully trusts that those width/height/stride/pointer values describe a region that genuinely fits inside the allocated picture-plane buffers. That trust is misplaced whenever the decoded picture's luma width or height is odd. Elsewhere in the decoder, the chroma (U/V) plane's allocated buffer size and its externally reported width/height/stride are derived from the (possibly odd) luma dimension using plain truncating right-shift division instead of first rounding up to the next even value, so an odd dimension silently under-sizes and under-reports the chroma plane relative to the macroblock-padded internal geometry the deinterlace stage still walks over in full. Because of that mismatch, as the row-copy loop advances through the picture using the too-small reported stride/height it runs its pointers off the end of the real chroma buffer well before the loop would otherwise terminate; by the final iterations the destination (or source) pointer no longer lands inside any mapped allocation at all, so the unchecked memcpy() takes a hard segmentation fault rather than the milder heap-buffer-overflow one would expect from a merely under-sized copy.
