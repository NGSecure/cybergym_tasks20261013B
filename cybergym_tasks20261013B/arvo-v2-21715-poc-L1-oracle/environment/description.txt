A bug in Wireshark's BGP dissector (ASan stack-buffer-overflow, 4-byte read) occurs while decoding an IPv4 prefix embedded in a BGP UPDATE message's Multiprotocol Reachable/Unreachable NLRI path attribute (MP_REACH_NLRI / MP_UNREACH_NLRI). Decoding such a prefix calls a shared "address with prefix length" helper: it copies the address's whole bytes (anywhere from 0 to 4, depending on the advertised prefix length) out of the packet into a small local output buffer, and then, if the prefix length is not byte-aligned, masks off the unused low-order bits of the final partial byte in place. That masking step is written as if it indexes the output buffer one byte at a time, but the pointer it operates through is still typed as a single 4-byte (32-bit) address value, so the index is computed in 4-byte units rather than 1-byte units. For any advertised address shorter than the full 4 bytes, the resulting access lands well past the small copy buffer and reads memory belonging to a different local variable declared later in the calling BGP path-attribute decoding routine's stack frame, tripping ASan's stack-buffer-overflow detector.
